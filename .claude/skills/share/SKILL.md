# /share — post a vault-chat update to Bluesky

The user runs this **passively** — small build-in-public posts after we finish something, not launch announcements. Match that energy. You drive the workflow; the user supplies the editorial taste (what's worth sharing, final wording).

**Bluesky-only.** Reddit was deliberately removed: its cadence (one big-event post every few months) is incompatible with build-in-public drip-feed, and the culture is hostile to anything that reads as automated. If the user ever wants a Reddit post for a milestone, they'll write it manually.

## Voice — build-in-public progress

- Lowercase, casual, no marketing copy, no exclamation points.
- "shipped X today" / "added Y this week" / "the weird thing about X is…" — dev journal, not press release.
- Honest about it being in-progress. Don't say "vault-chat now supports…" like it's a stable shipped product. Say "added voice mode to vault-chat this week" — first-person, in-flight.
- One specific observation > a feature list. The reader doesn't want bullets; they want a thought.
- End with the repo URL on its own line. URLs auto-linkify via facets.

Tone may shift later (user mentioned they may pivot). If they say so in-session, follow that for this run; do not edit this file unless asked.

## Workflow

1. **Infer the share from recent conversation.** If the user just invoked `/share` after we finished building/shipping/discussing something, that *is* the share — don't ask "what's the share?" Look at what we just did:
   - We just shipped a feature → that feature is the share.
   - We just had an insight (e.g. the voice-mode "which questions get asked" framing) → that insight is the share.
   - We just merged a release tag → the release is the share.
   - If context is genuinely ambiguous (e.g. fresh chat, user types `/share` with no preceding work), then ask.
2. **Pull supporting context** if needed:
   - Latest release tag: `git describe --tags --abbrev=0`
   - Commit range since prior tag: `git log <prev>..<latest> --oneline`
3. **Draft.** ≤290 chars, one post, no threads. URLs auto-linkify via facets so just paste them in plaintext. End with the repo URL: `https://github.com/carlwilsn/vault-chat`
4. **Show the draft.** User edits or approves. Iterate freely.
5. **On approval, post:**
   - `node .claude/skills/share/post_bluesky.mjs --text "..."`
   - Prints JSON on success: `{platform, ts, url, uri, cid}`. Non-zero exit + stderr on failure.
6. **Append to `devlog/posts.jsonl`** at the repo root, one JSON object per line: `{ts, platform, url, text}`. Create the file/dir if missing.
7. **Report the live URL back.** Don't editorialize about engagement metrics.

## Setup

If the script fails with `Credentials not found at ~/.config/vault-chat-share/credentials.env`, point the user at `.claude/skills/share/SETUP.md`. Do not try to create or guess credentials.

## Out of scope (v1)

- X / Twitter (paid API)
- Scheduled posts
- Image / video uploads
- Auto-trigger on release tags (intentionally manual — user is the editorial filter)
- Threads (one post per share; if it doesn't fit, tighten)

If the user asks for any of the above, flag the gap and ask before doing anything else.
