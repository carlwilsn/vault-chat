# vault-chat

vault-chat is Carl’s interface to pi, running on thinkbox with a Tauri laptop app,
a phone web app for alerts and notes, and voice. It is not AgentOS.

## Carl’s vault-chat instructions

- Done means Carl’s ask works for Carl, judged on the real app (and his laptop probe numbers for speed).
- Run the normal typecheck and tests before a ship request; nothing else is required.
  No proof cards, recordings, shipment proofs, real-data captures beyond what the
  ship script does itself, plans or progress reports.
- Talk to Carl only when an ask ships: one line, and for speed fixes his before and
  after probe numbers. Never invent missing measurements.
- No tracking files: no ASKS, PLAN, CURRENT or HANDOFF files. Carl's asks live in the chat.
- Sub-agents only to go faster on an ask, never for checking, auditing, owning or monitoring.
- Work in up to three independent lanes when Carl asks for parallel work. Each lane:
  fix → normal tests → ship request → read result; never duplicate another lane’s work.
- Use an agent/<name> branch in your own clone. Push it to publish, then write
  ~/agent-work/vault-chat/ship-requests/<unique>.req with exactly two lines:
  the branch name and a plain one-line title. Read its .result and .log.
  Only the installed ship script promotes main; its watcher publishes accepted
  main to GitHub. Do not duplicate that push; verify the remote SHA.
- Shipped means the box and Carl’s laptop run the release and autonomous checks on
  the real app pass (Carl’s native laptop probe for speed). Do not ask for a
  greenlight or wait for Carl’s confirmation.
- No source recovery or rollback of accepted work; no new shipping machinery,
  systemd-run units, owners, continuations, handoffs, receipts or waiting chains.
  Do not edit the installed simple-ship copy.
- Keep conversation ownership separate from the viewer/file workspace. Vaults and
  projects are many-to-many; the vault picker lists vaults, not project ownership.
- Ask only for money, irreversible actions or visual taste. Never read/copy secrets,
  server env/token files or private keys, or print keys. Other vaults’ .vault-chat
  and .git are private. Keep tests muted and off live ports 8848/8857.

## Source map

- server/: box HTTP server and pi integration; src/: React/Tauri laptop client.
- phone/ (the phone app: alerts and notes only), voice-pipeline/ (voice transport). board/ is a placeholder only for the installed ship script's fixed board gate (board/README.md).
- package.json: normal typecheck/test commands. memory/: short source facts only.
- Inline HTML (src/inlineHtml.ts): `![label](.vault-chat/visuals/x.html)` in a reply shows that vault page live and
  interactive in the chat (laptop pane, fullscreen): sandboxed, no network, so inline its scripts/data. Charts,
  widgets, explainers, mockups. For the app's look, link `<link rel="stylesheet" href="/app-styles.css">` and use
  the app's own classes (only classes src/ uses exist; anything else inline `style`); for exact fidelity, the real
  components in the preview harness (preview/, `npm run preview`, `?scenario=`) shot with RecordUI.
- Inline web pages (src/inlineWeb.ts, src/InlineWebPage.tsx, src-tauri/src/web_embed.rs): `![title](https://…)` on its own line (not an image/video/PDF address)
  shows that public page live in the chat on the Windows/macOS app: a native browser view (wry, made outside Tauri's webview manager: no Tauri IPC, no app
  protocols, its own InPrivate data folder) laid over a placeholder and kept on its visible part as the chat scrolls; hidden when an app menu/dialog covers it.
  Back/Forward/Reload, Full window, Browser, Close. Public http(s) hosts only (no loopback/LAN/tailnet/*.ts.net); popups load in place; downloads refused.
  Phone, browsers, Linux, refused addresses or any failure: the title is a plain link.
- Live pages (src/liveBridge.ts): a vault .html that declares `<meta name="vc-capabilities" content="ask, mic">` gets `window.vc` after Carl's one-time Allow
  (per path + content hash): `vc.ask(prompt,{system})` streams an ephemeral read-only AI reply (`for await`, `.text()`), `vc.fetch(path, init)` reaches only what the
  granted capabilities cover (box-checked token), `vc.mic()`/`vc.play()`, `vc.theme`/`vc.size`; no `<form>` (sandboxed), buttons + keydown. The services a page may name
  (ask, mic, voice-lab = `tool:voice-lab.*`, persist (an older word that opens nothing), theme, state, log, converse, catalog) are declared once in src/liveServices.ts; an unknown
  name is refused (`vc.refused`); `vc.services` lists what was granted, `vc.service(name)` returns its function. `state`: `vc.state.get/set/subscribe`, the page's own state as plugin.state records in the box's one log (src/pluginRecords.ts, server/pluginState.ts), the same in every view; `log`: `vc.log(record)` appends a plugin.log record. `converse` (src/pluginConverse.ts): `vc.converse.start(text)` makes a real chat in the chat list (the box's own send intent, `via: "page"`, the page named in the turn's context), `vc.converse.send(convId, text)`, `vc.converse.list()`, `vc.converse.read(convId, {after})`; no other intent. `catalog` (src/pluginCatalog.ts, server/pluginCatalog.ts): `vc.catalog()` → {services, plugins}: every registered service and the vault's plugins (.html pages with a vc-capabilities / vc-mount manifest: id = vault path, name, mount, needs), read from the vault each time; the same list at GET /api/v2/plugin/catalog (app, loopback). Example: .vault-chat/visuals/live-chat-demo.html.
  Every vault .html also has its own link on the box, `https://<box>.<tailnet>.ts.net/p/<vault path>/` (`?vault=<name>` for a non-main vault; server/pageLink.ts):
  the same page and `vc` in a plain tab or on the phone, opened only through `tailscale serve` as an allowed login (no loopback, no token).
  In-process mount (src/mountHost.ts): a page with `<meta name="vc-mount" content="in-process">` runs in the app itself, no iframe: its styles + markup in a shadow root, its inline `<script type="module">` exporting `mount(el, api)` (widget contract: api.size/onResize/theme/onTheme/path; api.listen/timer/effect, undone on unmount; return a cleanup); anything it throws becomes an error card with Reload. No vc services there yet.
  Supervisor (src/pluginSupervisor.ts, server/supervisor.ts): a page's on/off is plugin.desired records in the one log (`{plugin, state: running|stopped, from?, by, reason?}`;
  newest word in effect wins, `from` = later, e.g. an end date) and plugin.budget records (`callsPerMinute`: over it the box writes `stopped`, by budget). Stopped: the box
  gives it nothing (no token, gateway 403, its page not served: raw, /p/ link) and every view (viewer, chat inline, iframe or in-process, phone, link) takes it
  down and shows "<name> is turned off" + Turn on; running again, it mounts afresh. Write one with the agent's box:pages (server/model/pages.ts) or POST /api/v2/supervisor; GET reads the records.
  Layout (src/layoutOps.ts): the screen's layout as data and ops (panes and files, split, left panel, chat, window and column sizes), `api.host.layout.get()/apply(ops)` for plugins and the agent's `Layout` tool (server/layoutTool.ts, over Show's signal + ack channel, laptop only); every apply answers with the layout read back from the screen. Layout `openChat {id}` (a chat id, "main", "project-<slug>") switches the chat pane through app/chats' own `open` (a plugin signal), then reads the layout back.
  Control link (server/deviceLink.ts): Screen, Layout, PluginRead/PluginAct, LaptopBuild, the gate's drive signals (server/convlog/log.ts CONTROL_SIGNALS) ride every vault's feed, whatever vault the app has open (Show stays the open vault's); the link is tracked per device across vaults (up/down since when and why, the chat link beside it, unanswered requests), said by the tools when down and shown in GET /api/v1/health `links`.
  Screen (server/screenTool.ts): the agent sees the real laptop app. A "capture" signal on Show's channel; the laptop (the device host supplying `capture`) draws its own window from the DOM (src/screenCapture.ts: the document cloned with form values, scroll offsets, canvases and images as pixels, in an SVG foreignObject, onto a canvas; sandboxed live pages as a labelled box; window only, never the desktop), downscaled to <= 1600 px wide, and acks with the PNG (src/captureOnLaptop.ts); the box checks the PNG's own size and the tool returns it as an image, or offline / no answer / the laptop's reason. Plugins get the same as `api.host.capture(target)`.
  LaptopBuild (server/hostBuild.ts): which build the laptop app runs. At each launch the main window reports its build (frontend version + revision, native version, runtime, launch-to-interactive, the server it runs if any; src/hostBuild.ts) to POST /api/v1/host/build; the box logs it (<state>/logs/host-builds.jsonl, newest per host in <state>/host-builds.json). The tool asks live (a "build" signal, acked) and shows the last report; `action: "wake"` leaves a one-shot watcher (<state>/host-build-watch.json) and an installed app's report of a different (or the named) build adds a durable wake for that chat (server/engine/wakes.ts), so the agent checks the laptop then instead of polling. Native builds come only through the updater (ship.yml release, latest.json; "Install & restart"); the frontend also comes as a core bundle (below), reported as `core` apart from the native version.
  Hot core (src/coreBundle.ts, server/coreBundles.ts, scripts/core-publish.ts, src-tauri/src/core_loader.rs, src/coreFollow.ts): the laptop app's whole frontend is a part, `app/core`. While Carl's setting corePublish is true (the default; false: nothing is built, a keep on app/core is refused), the box builds it from each new main itself (through the existing StartJob path, startJobWith; never GitHub/latest.json) and stores it outside the vaults (<state>/core-bundles/<version>, version = first 8 hex of the manifest's sha256). There is no Try step: the newest undecided built bundle (server/coreBundles.ts newestUndecidedCore) goes through the gate once (server/gate.ts landCore, every minute with the publisher) and, passed, is a plugin.change keep by "gate" (current for every launch; the laptop takes it when Carl presses OK on the bottom-right Ready card, src/coreReady.ts); a switch back has the loader run the core in effect at once (followCoreNow). Every swap keeps the screen (src/coreSwap.ts: on the swap's load index.html shows no splash and keeps the new screen hidden, so the webview holds the old frame, until the new bundle has put back the open chat, its scroll, the composer draft, the panes and panels; the leave guard stands aside for it in every window). GET /api/v2/core is the offer (what the records keep), /api/v2/core/<v>/manifest.json and /files/<path> its bytes; health `core`. The manifest declares its needs (the native commands it invokes and shell plugins it imports, scanned from src/; CORE_BOX_API): the loader refuses a bundle its shell lacks a command for, the laptop one needing a newer box. The native loader (outside every bundle) checks every hash, serves the bundle at the app's own origin, and requires `core_ready` within 30 s of each load (main.tsx calls it at first paint); a throw before ready, no ready, or a launch whose last load never came up falls back to the previous bundle, then the baked one, and the laptop writes a plugin.change switch by "auto". A kept bundle not yet running is fetched and checked, then waits for Carl's OK on the Ready card (Later hides it until a newer version or the next start); nothing swaps without OK, never an installer. Only native changes need a release. Every command the source invokes must be in lib.rs shell_commands! (a test checks it), else no bundle could run. The command set is versioned per command: src-tauri/shell-abi.json (generated by `npx tsx scripts/shell-abi.ts`, kept current by server/test/shellAbi.test.ts) gives each command's signature (the arguments the bundle passes, the result) and its version; the manifest's needs.abi names the version of every command the bundle calls, and the loader (core_loader.rs, and nextCoreStep when the shell reports its abi) refuses a bundle built against another signature of one. Changing a command's arguments or result makes every bundle needing it wait for the installer: to keep new bundles running on old shells, add foo_v2 instead and keep the old one until no bundle needs it. The keep's `what` says what a bundle changes over the core in effect (the box's git log of main: titles, the paths each touches, `Look:` trailers; src/coreBundle.ts coreCard). After every swap the new page says what runs ("Now running frontend …" or "Couldn't switch: <why>. Still on …"; src/coreFollow.ts checkSwapOutcome).

  Migration drafts (src/migrations.ts, server/migrations.ts, id `migrate/<name>`): a plugin's state reshaped by asking, expand / contract. `.vault-chat/migrations/<name>.draft.js` (`// @vc-change <what>`, `export const plugin = "app/<name>" | "box/<name>" | a page's vault path`, `export function migrate(oldState) => newState` over the whole state) goes through the gate: its dry run = GET /api/v2/migrations/try (migrate on a copy of the real state in a worker_thread, 5 s / 128 MB, nothing written); passed, the gate's Keep (POST /api/v2/supervisor, async) runs migrate, writes a backup (state + every record of the plugin) to $VC_MIGRATION_BACKUP_DIR or <stateDir>/backups/migrations (no backup, no keep), then one `plugin.epoch` record {plugin, epoch, from, state, migration, version, kept} and the plugin.change record; the draft becomes <name>.kept-<version>.js. From then the box writes that plugin's sets as `plugin.epoch.state` {epoch, key, value} (server/pluginState.ts write); plain plugin.state records are never rewritten, so an older app or phone reads the old shape. Switch back = another plugin.epoch record (the epoch left, its state as the box kept it; folds keep `others` epochs on the box only); a second switch goes forward; only the newest migration of a plugin switches. Folds (src/pluginRecords.ts foldPluginState) apply only the epoch in effect; PluginState carries `epoch`. Nothing migrates at boot.

  (an effect of its run: gone when it stops). The agent reaches every such plugin through two generic tools, PluginRead (list live plugins' offers; read one's state + recent events) and PluginAct
